# How Does PolyTrack Know a Run Was Driven by a Bot?

### A deterministic-replay and statistical-detection analysis, with math and runnable code

*Companion code: [`bot_detection.py`](bot_detection.py) — pure-numpy, runs in seconds.*

---

## Abstract

PolyTrack (Kodub) stores every leaderboard time as a **recorded input sequence**
played back through a **bit-exact, fixed-timestep physics engine**. This single
architectural choice does two very different jobs that are constantly confused:

1. It makes times **verifiable** — you cannot upload a number, you upload the
   keystrokes that *produce* the number, and anyone can re-simulate them. This
   defeats *forged times* completely.
2. It does **not**, by itself, distinguish a fast human from a fast bot. A bot
   that submits a legal, re-simulatable input trace produces a 100%-valid run.
   Detecting that the *driver* was an optimizer rather than a person is a
   **statistical** problem, not a verification problem.

This paper separates those two layers cleanly. Part I derives why determinism
makes replay verification exact (and what it can and cannot catch). Part II
builds a principled statistical detector from the *fingerprint of a bot's input
timing*, with hypothesis tests, a likelihood-ratio classifier, ROC analysis, and
an information-theoretic bound on evasion. All claims in Part II are demonstrated
by the companion simulation.

> **Epistemic note.** The PolyTrack *client* architecture in Part I (deterministic
> 1 ms physics, input-recording leaderboard at `vps.kodub.com`, ghost replays) is
> established fact, observed directly while building this repo's headless sim. The
> server-side *detection policy* in Part II is **not** published by Kodub; Part II
> is the detector *I would build*, derived from first principles and validated in
> simulation. It is labeled as a model throughout.

## Part I — Verification: why a fake *time* is impossible

### 1. The run is the input, not the number

A PolyTrack run is integrated at a **fixed timestep** `Δt = 1 ms` (1000 Hz). The
engine is a Bullet build compiled to Emscripten/WASM and is **deterministic**:
given the same initial state and the same input stream, it returns bit-identical
results on every machine (this repo's headless port reproduces the game's own
self-test exactly). Formally the simulation is a deterministic map

$$
s_{k+1} = F\big(s_k,\; u_k\big), \qquad s_0 = s_{\text{init}},
$$

where $s_k \in \mathbb{R}^{n}$ is the full physics state at frame $k$ (the
227-byte car struct, plus the rigid-body world), and $u_k \in \mathcal{U}$ is the
control input on frame $k$ — a bitmask of `{left, right, throttle, brake}`. The
finish time of a run is just the first frame the goal predicate holds:

$$
T = \Delta t \cdot \min\{\,k : \text{goal}(s_k)\,\}.
$$

Because $F$ is a pure function, $T$ is a **deterministic functional of the input
sequence alone**:

$$
T = \mathcal{T}(u_{0:K}), \qquad u_{0:K} = (u_0, u_1, \dots, u_K).
$$

So the leaderboard does not need to trust a reported time. It stores $u_{0:K}$
(this is exactly what the "ghost"/replay feature plays back) and can recompute

$$
\hat T = \mathcal{T}(u_{0:K})
$$

independently. **Validation is the assertion $\hat T = T_{\text{claimed}}$.**

### 2. What this catches, with certainty

Let an attacker submit a claimed time $T^\star$ with *some* attached input
$u_{0:K}$. Two failure modes are caught with probability 1:

- **Forged time, no/handwaved inputs.** If $\mathcal{T}(u_{0:K}) \neq T^\star$,
  reject. There is no input stream that finishes in 0.0 s, so "I drove it in
  0.0 s" cannot be backed by a replay.
- **Impossible physics.** Any state edit (teleport, speed hack) that is not the
  image of $F$ under *some* legal input is unreachable: there is no $u$ with
  $F(s_k,u) = s_{k+1}^{\text{hacked}}$, so the replay diverges from the claim.

Determinism is what makes this a *proof*, not a heuristic. Compare to a
non-deterministic engine (variable timestep, RNG, float-order drift across CPUs):
there $\hat T \neq T$ even for *honest* runs, the equality test must become a
tolerance $|\hat T - T| < \varepsilon$, and that slack is exactly the room a
cheater needs. PolyTrack's fixed 1 ms step removes the slack.

### 3. What this **cannot** catch — the crux

Replay verification checks that *the input produces the time*. It says nothing
about *who or what produced the input*. A bot in this repo does precisely the
honest thing:

> run the **real** physics $F$ headless, search/learn an input sequence
> $u^\star_{0:K}$ that minimizes $\mathcal{T}$, then replay $u^\star$ in the
> browser.

That submission satisfies $\hat T = T_{\text{claimed}}$ **exactly**, because it
*was* generated by $F$. From the verifier's point of view it is a perfect run.
Verification therefore reduces the problem to: *is this legal, re-simulatable
input stream the kind of thing a human hand produces?* That is Part II.

## Part II — Detection: the statistical fingerprint of a bot

### 4. Threat model and the core asymmetry

We observe one or more legal input traces from a player and must decide between

$$
H_0:\ \text{human driver} \qquad\text{vs.}\qquad H_1:\ \text{automated driver.}
$$

The leverage comes from a structural asymmetry between how the two *generate*
$u_{0:K}$:

| | Human | Bot (search / RL) |
|---|---|---|
| Time base | continuous wall-clock, sampled by the input system | the 1 ms grid itself is the planning unit |
| Timing law | reaction/motor delays → **ex-Gaussian** intervals | optimizer output → tight, can be frame-adjacent |
| Repeatability | high lap-to-lap variance | near-deterministic replay |
| Optimality | bounded by perception + dexterity | bounded only by search budget |

Each row is a measurable feature. None is individually conclusive; **pooled**,
they separate cleanly (and the pooling is just a likelihood ratio, §7).

### 5. Detector 1 — sub-frame phase (the sharpest single tell)

A human key event happens at a continuous wall-clock time $\tau$. The input
layer records it at frame $k = \mathrm{round}(\tau/\Delta t)$, but the *residual*

$$
\phi = \frac{\tau}{\Delta t} - \Big\lfloor \frac{\tau}{\Delta t} \Big\rceil
\pmod 1
$$

— the **sub-frame phase** — is, over many events, distributed
$\phi \sim \mathrm{Uniform}[0,1)$. There is no reason a human's muscle twitches
align to the engine's millisecond grid.

A bot that *plans on the grid* emits events at integer frames, so its phase is a
spike at $0$: $\phi \equiv 0$. Test $H_0:\ \phi\sim U[0,1)$ with a binned
chi-square over $m$ bins,

$$
X^2 = \sum_{j=1}^{m} \frac{(O_j - E_j)^2}{E_j}, \qquad E_j = \frac{N}{m},
\qquad X^2 \overset{H_0}{\sim} \chi^2_{m-1}.
$$

In the simulation (`--players` off, one run each) this is brutal:

```
[D1 sub-frame phase chi^2]  human stat=  12.33 p=0.195   |  bot stat=1080.00 p=9.58e-227
```

The human is consistent with uniform ($p\approx0.2$); the raw bot is rejected at
$p\approx10^{-227}$. **Caveat:** this tell evaporates if the bot dithers its
phase before submitting (§8) — which is exactly why we need more than one
detector.

### 6. Detector 2 — the inter-event interval law

Human inter-response intervals are textbook **ex-Gaussian**: a Gaussian motor
component convolved with an exponential decision tail,

$$
f_{\text{exG}}(x;\mu,\sigma,\tau)=\frac{1}{\tau}\,
\exp\!\Big(\frac{\mu-x}{\tau}+\frac{\sigma^2}{2\tau^2}\Big)\,
\Phi\!\Big(\frac{x-\mu}{\sigma}-\frac{\sigma}{\tau}\Big),
$$

with a hard floor around 10–12 ms (you cannot voluntarily issue distinct presses
faster than that). A bot has **no such floor**: an optimal plan routinely places
control changes 1–3 ms apart (frame-adjacent), and its intervals cluster far more
tightly than any reaction-time law allows.

Compare the empirical interval CDFs with a two-sample **Kolmogorov–Smirnov**
statistic

$$
D = \sup_x \big| F_{\text{obs}}(x) - F_{\text{human}}(x) \big|,
$$

calibrated against a reference human distribution. Simulation:

```
[D2 interval-law KS]  D=0.513  p=1.75e-14
```

A separation of $D\approx0.5$ is enormous. The single most human-impossible
observable is the **fraction of frame-adjacent intervals** ($\le 3$ ms); we use
that scalar directly in the classifier because, unlike phase, it **survives
phase-dithering** (dithering moves events within a frame, it cannot widen a 2 ms
true gap into a human 30 ms gap without changing the racing line).

### 7. Detector 3 + pooling — consistency and the likelihood ratio

Across $R$ repeated attempts, lap time has **coefficient of variation**

$$
\mathrm{CV} = \frac{\mathrm{std}(T_1,\dots,T_R)}{\mathrm{mean}(T_1,\dots,T_R)}.
$$

Humans sit around $\mathrm{CV}\sim5\%$; a bot replaying a fixed plan is at
$\mathrm{CV}\lesssim0.3\%$. (A bot *re-deriving* a plan each time is noisier, so
CV is a weaker, supporting feature — hence its small weight below.)

**Pooling.** The Neyman–Pearson optimal test combines features by their
log-likelihood ratio,

$$
\Lambda(x) = \log \frac{p(x\mid H_1)}{p(x\mid H_0)}
\;\overset{H_1}{\underset{H_0}{\gtrless}}\; \eta,
$$

and a logistic-regression score is the LLR under a Gaussian-feature / linear
model — exactly what the companion code fits over the four features
$x=(X^2_{\text{phase}},\ \text{frac frame-adjacent},\ \text{action entropy},\ \mathrm{CV})$.
On held-out players:

```
POOLED LLR CLASSIFIER  (mimic=off)
    chi2_phase             +2.831     <- biggest contributor
    frac_frame_adjacent    +2.533
    action_entropy         -1.105
    lap_CV                 -0.878
held-out ROC AUC = 1.0000   accuracy@0.5 = 1.000
```

Detector 4 (action **entropy**, $H=-\sum_a p_a\log_2 p_a$) is a weak,
sign-meaningful add-on: a clean optimal plan is slightly *lower* entropy than
fidgety human input, hence the negative weight.

### 8. Evasion and the detectability limit

Can the bot hide? Run the same experiment with `--mimic`, where the bot adds
sub-frame jitter and inflates lap-time CV to look human:

```
POOLED LLR CLASSIFIER  (mimic=ON)
    chi2_phase             -0.083     <- D1 NEUTRALIZED
    frac_frame_adjacent    +4.619     <- now carries the decision
    action_entropy         -2.101
    lap_CV                 -0.267
held-out ROC AUC = 1.0000
```

This is the key qualitative result. Phase dithering **does** kill D1 — its weight
collapses to ~0, exactly as theory predicts. But the classifier just **re-weights
onto frame-adjacent intervals**, and AUC stays at 1.0. The reason is structural:

> Mimicking human *timing* statistics requires emitting genuinely
> human-impossible-to-improve-upon-by-waiting intervals **wider** than the
> optimal plan uses. But widening a control interval **changes the trajectory**,
> which costs time. There is a Pareto wall between *looking human* and *being
> world-record fast*.

We can state the limit information-theoretically. Let $P_0,P_1$ be the human and
(disguised) bot distributions over observable input features. The best achievable
detector accuracy is governed by total variation, and the **minimum number of
runs** $n$ to separate them at error $\alpha$ scales as

$$
n \;\gtrsim\; \frac{1}{\mathrm{KL}(P_1\Vert P_0)} \log\frac{1}{\alpha},
$$

by the Chernoff–Stein lemma. Evasion's job is to drive $\mathrm{KL}(P_1\Vert P_0)\to0$.
A *world-record* bot cannot: matching the WR forces low-CV, frame-tight inputs
that keep $\mathrm{KL}$ bounded away from 0, so $n$ stays small — **a few runs are
enough**. A bot willing to *throw away* the record can shrink $\mathrm{KL}$
arbitrarily and become undetectable from timing alone. In short: **the more
superhuman the time, the easier the bot is to catch.** This is the fundamental
tension a leaderboard-cracking project (this repo) runs into.

### 9. Other signals available to the server (beyond the trace)

The four features above use only the input trace. A real anti-cheat would also
have cheap, high-value side channels, which I list for completeness:

- **Holistic plausibility of the line.** Compare the trajectory to the human WR
  distribution; trajectories that are optimal to sub-frame tolerance on *every*
  corner are a strong $H_1$ signal even when timing is disguised.
- **Client integrity / environment.** Headless or instrumented clients, missing
  render-loop jitter, absent mouse-move entropy, replay submitted without a live
  session — all observable server-side and independent of §5–§8.
- **Rate & novelty.** A flood of WR-grade times across many tracks from one
  account in a short window is a population-level outlier; a sequential
  likelihood-ratio test (SPRT) over a player's submission stream flags it fast.
- **Cross-player collision.** Two "different" players submitting byte-identical
  or trivially-perturbed input traces ⇒ shared bot.

These don't replace the trace analysis; they raise $\mathrm{KL}$ in directions the
bot can't cheaply flatten.

## 10. Putting it together: the decision pipeline

```
            submission (claimed time + input trace u_0:K)
                              │
        ┌─────────────────────┴─────────────────────┐
        │  PART I — VERIFICATION (exact, P=1)         │
        │  re-simulate  T̂ = 𝒯(u_0:K)  with F          │
        │  reject if  T̂ ≠ T_claimed  or  state illegal│
        └─────────────────────┬─────────────────────┘
                              │ legal, re-simulatable run
        ┌─────────────────────┴─────────────────────┐
        │  PART II — DETECTION (statistical)          │
        │  D1 sub-frame phase   χ²  vs U[0,1)         │
        │  D2 interval law      KS / frac frame-adj.  │
        │  D3 cross-run CV                            │
        │  D4 action entropy                          │
        │  pool → LLR Λ(x) ≷ η  → human / bot         │
        │  + side channels (§9), SPRT over history    │
        └─────────────────────────────────────────────┘
```

**Verification is a proof; detection is a likelihood ratio.** Conflating them is
the single most common mistake in "how does the game catch bots" discussions.

## 12. Limitations & honesty

- Part II is a **model of a detector**, validated on **synthetic** human/bot
  generators, not on PolyTrack's (unpublished) server logic or on real captured
  traces. The generators encode the qualitative facts of §4; if real human input
  is grid-aligned for some reason (e.g. a 60 Hz input poll quantizing events),
  D1's power drops and the weight shifts to D2 — which is precisely the robustness
  the `--mimic` experiment demonstrates.
- The AUC of 1.0 reflects well-separated synthetic classes; treat it as
  "these features are individually and jointly informative," not a real-world
  catch rate.
- The honest takeaway for this repo's goal stands regardless of those details:
  **a verifiable run is easy; a verifiable run that is statistically
  indistinguishable from a human *and* still a world record is provably hard.**
